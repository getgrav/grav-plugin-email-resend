# v1.0.1
## 09/05/2026

1. [](#bugfix)
    * **Set up now repairs a webhook whose address has changed.** A store that generated a new secret, or lost its settings, was told nothing was registered while Resend still held a webhook at the old address, and pressing Set up made a second one — with a second signing secret the store never sees, so every event through it would have been refused. Set up now recognises the store's own webhook by its endpoint and moves it to the new address with `PATCH /webhooks/{id}`, which mints no new secret, so the one already saved carries on working.

# v1.0.0
## 09/05/2026

1. [](#new)
    * Initial release. Resend integration for the Email plugin, over Resend's API or over their SMTP server, through Symfony's own Resend mailer bridge. Resend's SMTP user is the word `resend` for every account and the password is the same API key, so there is one field to fill in rather than three.
    * Delivery reports. This plugin tells the Email plugin everything it knows about Resend through the Email plugin's provider contract: how to read and check a delivery webhook, how to create one from the API key you already pasted in, what a sending domain's DNS has to say, and what the transport does to a custom header. Anything on the site that records bounces, complaints, opens and clicks — the KahunaCart Newsletter add-on today — asks the Email plugin for it instead of carrying its own copy, so Resend renaming a field is one plugin to update rather than several. The webhook reader moved here out of the newsletter add-on, where it had been the only thing reading these payloads.
    * A one-press setup for the webhook. Anything that shows a Set up button hands this plugin the address, and it creates the webhook in Resend for the seven events that matter and saves the signing secret Resend hands back in the same answer. That secret is the part everybody misses doing it by hand: Resend shows it once, a webhook without it looks perfectly healthy in their dashboard, and every event arriving at your site is refused. Pressing the button twice leaves one webhook, and a key that is not allowed to manage webhooks comes back with Resend's own sentence plus the setting to change.
    * A domain lookup. With an API key filled in, this plugin reads the DKIM selector and the sending subdomain your account actually has straight out of Resend, rather than guessing. That matters more for Resend than for most: Resend publishes DKIM as a TXT record rather than as a CNAME into a zone of theirs, so there is no convention for anything to check a selector against, and asking is the only honest answer. Resend sends through Amazon SES, so the SPF include is `amazonses.com` and the return path is Amazon's too — that is correct, not a misconfiguration.
    * `email.failed` and `email.suppressed` are read, as the contract's `dropped`. Both are Resend refusing to send at all — the first for a reason of its own, an unverified domain or a quota, and the second because the address was already on the account's suppression list — and neither was ever handed to a receiving server, so neither is a bounce. Each of them says which of the two refusals it was, so nothing downstream has to guess: `email.suppressed` is the address, Resend will refuse the next message to it as well, and a store may treat it as permanent; `email.failed` is the message, its own documented reason is `reached_daily_quota`, and a store that suppressed on one would take a subscriber off its list for the store's own sending limit. Resend's own words for why come through on the event either way.
    * The header a send id travels in, and the tag that carries it back, are named by the Email plugin rather than by this one. The header is `X-Grav-Send-Id`, or whatever `providers.send_header` in the Email plugin's configuration says, and the tag is that name in the alphabet Resend allows in a tag key — `grav-send-id`. Both used to carry KahunaCart's name, which was another product's name in a Team Grav plugin.
    * A test suite: Resend's own documented webhook payloads read field by field, Svix's published signature vector plus forged, stale and unsigned requests refused, the setup call against a stand-in HTTP client, the DNS lookup, and the Symfony bridge exercised against the Symfony Mailer the Email plugin actually ships.
